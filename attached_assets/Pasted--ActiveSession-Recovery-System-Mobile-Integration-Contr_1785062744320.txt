# ActiveSession Recovery System — Mobile Integration Contract

> **Source of truth:** `artifacts/api-server/src/services/session/activeSessionManager.ts`
> **Do not guess.** Every field, type, and enum in this document is extracted verbatim from the backend implementation.

---

## Overview

### What ActiveSession represents

An **ActiveSession** is a normalized, real-time snapshot of a user's current in-progress activity — either a ride (car / scooter / delivery) or a shuttle booking/trip. It is the single authoritative source the mobile apps must use to restore UI state after any interruption: app background, network loss, socket reconnect, or cold start.

### Why it replaces old recovery mechanisms

The old approach required apps to call multiple ride/trip/booking endpoints and reconcile state themselves. The ActiveSession system centralizes that logic server-side. Apps now call one endpoint (or receive one socket event) and get a complete, ready-to-render snapshot.

### Which applications consume it

- **Passenger App** — consumes `PassengerActiveSession` (ride or shuttle booking view)
- **Driver App** — consumes `DriverActiveSession` (ride or shuttle trip view)
- **Admin Dashboard** — does **not** consume these endpoints; this contract is for mobile clients only

## API Contract

### GET /api/passenger/session

| Property | Value |
|---|---|
| Method | `GET` |
| Full path | `/api/passenger/session` |
| Authentication | Required — Bearer JWT (`role: "user"`) |
| Success status | `200 OK` |
| Error status | `500` — `{ "error": "Failed to fetch passenger session" }` |

**Response envelope:**
```json
{
  "data": <PassengerActiveSession> | null
}
```

`data` is `null` when the passenger has no active session.

---

### GET /api/driver/session

| Property | Value |
|---|---|
| Method | `GET` |
| Full path | `/api/driver/session` |
| Authentication | Required — Bearer JWT (`role: "driver"`) |
| Success status | `200 OK` |
| Error status | `500` — `{ "error": "Failed to fetch driver session" }` |

**Response envelope:**
```json
{
  "data": <DriverActiveSession> | null
}
```

`data` is `null` when the driver has no active session.

## Session Types

### Passenger session types

The `sessionType` field is the discriminator.

| `sessionType` | Description | Primary identifier |
|---|---|---|
| `"ride"` | Car, scooter, or delivery ride | `rideId` |
| `"shuttle_booking"` | Shuttle bus booking | `bookingId` |

**How identified:** The backend checks for an active ride first (priority), then an active shuttle booking. A passenger will never receive both simultaneously.

**Sub-type within `"ride"`:** use `vehicleType` — `"car"` | `"scooter"` | `"delivery"`.

---

### Driver session types

| `sessionType` | Description | Primary identifier |
|---|---|---|
| `"ride"` | Car, scooter, or delivery ride | `rideId` |
| `"shuttle_trip"` | Shuttle bus trip | `tripId` |

**How identified:** The backend checks for an active ride first (priority), then an active shuttle trip.

## Status Rules

### Passenger ride statuses (`PassengerRideSession.status`)

| Status | Active? | Meaning | Client should |
|---|---|---|---|
| `"requested"` | ✅ Active | Ride created, not yet dispatched | Show "Finding your driver" |
| `"searching"` | ✅ Active | Dispatch rounds running | Show "Searching…" + dispatch round info |
| `"driver_assigned"` | ✅ Active | Driver accepted, en route to pickup | Show driver en route |
| `"driver_arrived"` | ✅ Active | Driver is at pickup location | Show "Driver arrived" |
| `"active"` | ✅ Active | Ride in progress | Show ride in progress |

No terminal statuses are returned — a completed or cancelled ride produces `data: null`.

**Client rule:** If `data` is a ride session with any of the above statuses → show recovery UI. If `data` is `null` → clear session.

---

### Passenger shuttle booking statuses (`PassengerShuttleSession.bookingStatus`)

| Status | Active? | Meaning |
|---|---|---|
| `"pending"` | ✅ Active | Booking created, awaiting confirmation |
| `"confirmed"` | ✅ Active | Booking confirmed |
| `"boarded"` | ✅ Active | Passenger marked as boarded on the bus |

The linked `trip.status` also indicates the shuttle's overall state (see trip status values below).

---

### Shuttle trip statuses (inside `PassengerShuttleSession.trip.status`)

| Value | Meaning |
|---|---|
| `"scheduled"` | Trip exists, not yet started |
| `"waiting_driver"` | Awaiting driver assignment |
| `"driver_assigned"` | Driver assigned, not yet boarding |
| `"boarding"` | Passengers boarding |
| `"active"` | Trip in progress |

---

### Driver ride statuses (`DriverRideSession.status`)

| Status | Active? | Meaning |
|---|---|---|
| `"driver_assigned"` | ✅ Active | Driver accepted, heading to pickup |
| `"driver_arrived"` | ✅ Active | Driver at pickup |
| `"active"` | ✅ Active | Ride in progress |

Note: Driver does **not** see `"requested"` or `"searching"` — those are passenger-side only.

---

### Driver shuttle trip statuses (`DriverShuttleSession.status`)

| Status | Active? | Meaning |
|---|---|---|
| `"driver_assigned"` | ✅ Active | Trip assigned, pre-departure |
| `"boarding"` | ✅ Active | Passengers boarding |
| `"active"` | ✅ Active | Trip in progress |

## Socket Contract

### Event name

```
session:snapshot
```

### Who receives it

| Recipient | Room | Trigger |
|---|---|---|
| Passenger | Their personal passenger socket room | On every connect / reconnect |
| Driver | Their personal driver socket room | On every connect / reconnect |

The event is also emitted server-side (targeted to a specific user's room) when a session is **terminated** — see termination below.

---

### Payload structure

```typescript
// Active session:
{ data: PassengerActiveSession }   // passenger socket
{ data: DriverActiveSession }      // driver socket

// No active session / session terminated:
{ data: null }
```

---

### Meaning of `{ data: null }`

The session has been **terminated**. The client must immediately clear all session UI state and return to the idle/home screen.

This is emitted in the following scenarios:

| Scenario | Affected users |
|---|---|
| `completeRide` | Passenger + Driver |
| `cancelPassengerRide` | Passenger + Driver |
| `cancelDriverRide` | Driver only (passenger ride re-enters searching) |
| `completeTrip` (shuttle) | Driver + all boarded/completed passengers |
| `driverTripService.cancelTrip` | Driver + all pending/confirmed/boarded passengers |
| `adminOperationsService.cancelTrip` | Driver + all affected passengers |
| `completeExpiredTripFinancials` (shuttle auto-complete) | Driver + all boarded/completed passengers |

### Meaning when `data` contains a session

The server is sending the current complete snapshot. The client must render the appropriate screen based on `sessionType` and the current `status`.

## Client Recovery Flow

### App startup (cold start)

1. Authenticate and obtain a JWT.
2. Call `GET /api/passenger/session` (passenger) or `GET /api/driver/session` (driver).
3. If `data` is non-null → restore the appropriate session UI.
4. If `data` is null → proceed to idle/home screen.
5. Then connect the socket — the `session:snapshot` event will arrive automatically on connect and can be used to confirm or update the REST result.

### Socket connection (initial connect)

The server **automatically** emits `session:snapshot` to the socket immediately after a successful authenticated connection. No client-side emit is needed to trigger this.

### Socket reconnect

Same as initial connect. The server emits `session:snapshot` again automatically on every reconnect. The client must apply the received snapshot (overwriting any stale local state).

### Foreground resume (app comes back from background)

Not defined in backend implementation. Recommended client behavior: call the REST endpoint (`GET /api/.../session`) on foreground resume if the socket is not already connected and delivering a snapshot.

### Session termination (server-side)

When a session ends, the server emits `session:snapshot { data: null }` to the affected user's socket room. Additionally, if the user was **offline** at the time of termination, a push notification is sent. On receiving either the socket event or the push notification, the client must clear session state.
